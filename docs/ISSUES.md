# Open issues

One line per issue, numbered and never renumbered. Close an issue by moving it
to the Closed section with the date and what actually fixed it — do not delete
it.

A review or an audit does **not** get its own file. Its findings become issues
here, or they will be read once and forgotten.

Severity: **blocker** stops fabrication or release · **high** is a real failure
mode · **medium** costs time or quality · **low** is tidiness.

| I-028 | high | The 24 V source is undecided and it changes the input protection. From a panel supply off the mains, the present PTC + SS34 + SMBJ33A + TSR 1-2450 is adequate. | I-025 | high | Four-layer fabrication is hard to source in Egypt. The board is 4-layer because In1 carries three ground planes and In2 three supply planes. Measured today: 766 segments / 2761 mm on F.Cu, 278 / 3593 mm on B.Cu, 125 vias. Decide between a 2-layer redesign and ordering 4-layer from JLCPCB/PCBWay. |

## Firmware

These are failure modes for a protection device, not polish.

| # | Sev | Issue |
|---|---|---|
| I-036 | high | **Review 2026-09-07, reproduced on host with the real `main_8ch.c`: edits become live before persistence, and a failed EEPROM save is silently ignored.** `main_8ch.c:132` discards `persist_setpoint()` failure; UP/DOWN mutate the same variable used for protection. Starting with a stored 100 C limit, editing to 110 C and failing the save leaves a 105 C input permitted and the LCD showing `SP: 110 C SAFE`; EEPROM still contains 100 C. The existing config lock only protects initially blank/corrupt units. Separate candidate/active settings and handle save failure explicitly. Evidence: `production/analysis-20260907/review_app.c`, `review-behavior.log`. |
| I-037 | high | **Review 2026-09-07, reproduced on host: first-time setpoint entry hides the number being entered.** `protection.c:225` returns `SET SETPOINT` whenever config-locked, before the editing display branch. With blank EEPROM, SET then UP selects 201 C but still displays only `SET SETPOINT`; an operator cannot see the value they will store. Keep the run inhibit while displaying the candidate limit and save outcome. Evidence: `production/analysis-20260907/review_app.c`, `review-behavior.log`. |
| I-038 | high | **Review 2026-09-07, reproduced with the real MAX31856 bank driver and sensor monitor: post-init MISO stuck LOW is accepted as valid 0 C / no faults.** `temperature_max31856_bank.c:180-194` rechecks configuration only when its cached bit is clear, and clears it only for a local SPI transfer timeout. AVR SPIF indicates completion of clocking, not successful slave communication (Microchip AVR SPI developer documentation). Starting from 20 C, the host fault injection remains valid for 120 bad scans and first faults on scan 121, roughly 55 s at the nominal scan interval; a large temperature drop can instead trigger the rate check earlier. Add bounded runtime converter configuration/freshness checks and driver fault-injection tests; the stuck heuristic is not bus integrity verification. Evidence: `production/analysis-20260907/review_driver.c`, `review-behavior.log`; https://developerhelp.microchip.com/xwiki/bin/view/products/mcu-mpu/8-bit-avr/structure/spi-interface/ . |
| I-013 | high | **Specified now, still not measured.** The budget is in `firmware/include/app/app_config.h` and a `#error` fails the build if the constants drift out of it: 100 ms converter staleness + 456 ms scan + 57 ms loop + 10 ms relay = **623 ms** against the 1 s requirement. Every number is calculated. Measuring it on hardware - step the input past the setpoint, scope the contact - is still open, and the budget is only valid with the clock fuse set (`firmware/fuses.md`). |
| I-016 | medium | `RUN_PERMIT` is a static level with no read-back: a stuck pin, a shorted trace or a welded relay permits running forever and the firmware never knows. **Firmware side is written and waiting** - `hal/run_permit.c` implements the check and `BOARD_HAS_RUN_PERMIT_SENSE` in `mcal/board.h` compiles it out, because `PC2` is unconnected on REV A0 and reading it would invent faults from noise. Needs the `R53`/`R54` divider from `RELAY_LOW`, which is in the REV A1 change set (`docs/decisions/0010`). |
| I-032 | high | **Fuse specified; the crystal is deferred to REV A1.** `firmware/fuses.md` now pins `CKSEL = 0100` (internal RC 8 MHz) and BOD at 4.0 V, and `program.ps1` verifies both by read-back. What remains is the hardware half. Original text: **No crystal, and the clock fuse is unspecified.** `U1.12/13` (XTAL1/XTAL2) are deliberately unconnected (`populate_schematic.py:474`) and there is no oscillator in the BOM, so the ATmega32A runs on its internal RC. Two consequences nothing in the repo covers: (a) the factory `CKSEL` default is internal **1 MHz**, but the firmware builds at `F_CPU=8000000UL`, so every `_delay_ms` runs 8x long — the 500 ms scan becomes 4 s and `R-3`'s 1 s trip is missed by four times, silently, on a correctly built image; (b) the internal RC is spec'd to a few percent over voltage and temperature, which is outside what an 8-bit UART frame tolerates, so `R-9` (Modbus RTU) is **not** "hardware ready" as `docs/GOAL.md` claims — and the board is already routed with no crystal footprint. Extends `I-015`, which names only `BOD`. No decision record exists for crystal versus internal RC. |
