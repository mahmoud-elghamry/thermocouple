## 1. MCP server versus our scripts, plainly

An **MCP server is a callable interface for an AI client**. It advertises named operations and their arguments, accepts a request, executes some backend operation and returns a result. Being an MCP server does not imply a special router, a correct rule engine, or a connection to the live editor. The backend determines those things.

Our **scripts implement specific engineering work**: generate this board family, place these parts, finish these routes, measure these relationships, and refuse a release when its gates fail. A person, an agent's shell tool, another script, or an MCP wrapper can call them. Wrapping `maze.py` in MCP would change how the agent invokes it, not its routing algorithm.

```text
AI client ──MCP call──> Konnect ──IPC──> running PCB Editor
                              ├─file engine──> saved schematic / supported offline PCB edits
                              └─kicad-cli──> ERC, DRC, exports

Person / AI shell ──> Thermo scripts ──pcbnew──> closed-board files
                                   ├─stdlib parser──> focused read-only audits
                                   ├─kicad-cli──> native gates / release outputs
                                   └─DSN──> Freerouting ──SES──> pcbnew import

Thermo's schematic build ──kon.py / MCP stdio──> Konnect
```

The last path matters: **the scripts and MCP are already combined**, not competing alternatives. `docs/TOOLS.md` says the schematic build writes through Konnect over stdio.

Use Konnect for a bounded query or edit that benefits from the live PCB editor and undo. Use the generator for intentional regeneration, and the finishing scripts for repeatable board-specific repairs with KiCad closed and the writer guard satisfied. Use the stdlib checkers for fast inspection without loading KiCad. Use `kicad-cli` and the project gates for authoritative saved-design validation and release evidence.

**IPC access is not the same as native push-and-shove routing.** A server able to create track segments can still be placing geometry without invoking KiCad's interactive router. Similarly, a tool named `run_drc` may simply call the same `kicad-cli` already used here. KiCad documents its separate-process IPC architecture in the [official API overview](https://dev-docs.kicad.org/en/apis-and-binding/ipc-api/).

### Corrections to assumptions in the existing notes

1. **Do not describe all Konnect schematic writes as live IPC.** Its current upstream [backend table](https://github.com/mixelpixx/Konnect#how-it-works) says schematic editing uses its atomic S-expression engine; PCB editing uses IPC. The existence of schematic types/handlers in a KiCad binary does not demonstrate that a particular Konnect tool uses them. Preserve editor/file ownership discipline per operation.
2. The Windows named-pipe problem is real in the local decision record. Upstream's [0.12.0 release notes](https://github.com/mixelpixx/Konnect/releases/tag/v0.12.0) list named-pipe discovery (#530) and refusal of stale locked-file fallback (#486). **Do not remove the explicit socket setting merely because a newer release exists**; verify the actual serving build and exact-target behavior first.
3. The licence uncertainty has materially better primary evidence now. [Konnect COMMERCIAL.md](https://github.com/mixelpixx/Konnect/blob/main/COMMERCIAL.md) explicitly permits internal company use and says manufactured boards/design files are the user's; a separate MCP client/script is not brought under copyleft merely by communicating with Konnect. Distribution of Konnect or external access to a modified hosted version has different conditions. This is upstream's express statement, not a legal determination; the README's broader business wording is inconsistent with that detailed clarification. Commercial agreement pricing is **UNVERIFIED / by quotation**. No licence-driven MCP migration is justified by the old wording alone.
4. “IPC cannot verify/export” was a **dated observation of the local build**, not a permanent property of MCP or every future IPC build. Konnect currently documents CLI checks. KiPilot advertises newer build-gated export jobs. Qualify those capabilities against the installed runtime; do not infer them from enums or a server's tool names.

### Why custom clearance rules are the decisive test

Thermo does not have one universal clearance value. The local wrapper translates selected Contact/Chassis class pairs and adds rounding margin, while the maze has its own conservative domain model. **Neither establishes that arbitrary `.kicad_dru` semantics are transported to another engine.** A server that can read or write the rule text has also not proved its router evaluates that text.

The distinction is especially important for conditional exceptions, object types, rule precedence, domain boundaries and filled zones. The project's I-129 record describes a zone-sensitive relay-area exception: a copied rule file can be syntactically valid and still have a broader effect than intended. That issue record was read; its geometry was not remeasured here.

KiCad's [10.0 PCB manual](https://docs.kicad.org/10.0/en/pcbnew/pcbnew.html#routing-tracks) explicitly states that its interactive router respects object-specific custom clearances. This is the best confirmed finishing path when those semantics matter, although it does not prevent every DRC category. The [native DRC documentation](https://docs.kicad.org/10.0/en/pcbnew/pcbnew.html#design-rules-checking) still requires final checking, fresh zone fill and appropriate schematic parity.

Consequently, **using native KiCad Shove with an engineer is a stronger rule-preserving finishing option than swapping one generic MCP for another**. Unlock only the necessary neighbouring copper; an agent emitting independent line segments through IPC is not equivalent to Shove. For repeatable agent work, retain reviewed route lists and deterministic replay, then native validation.

Konnect's own new routing integration also has a material boundary: its [tagged 0.13.0 README](https://raw.githubusercontent.com/mixelpixx/Konnect/v0.13.0/README.md) limits the first supported Specctra profile to fixed straight tracks and through vias, rejecting unlocked routing, arcs, zones and unsupported geometry. Check admissibility before assuming it can replace `route24.py` on a poured, partly routed board. Freerouting's upstream [licence file](https://github.com/freerouting/freerouting/blob/master/LICENSE) confirms GPL version 3.

## 4. What adoption would actually mean

### Recommended evaluation order

1. **Identify the current serving Konnect build before planning an upgrade.** The registration path alone does not prove 0.11.1 is still running. Keep the existing explicit Windows socket setting. Evaluate a pinned release, not unreleased `main`, without installing bundled hooks/skills globally as a side effect.
2. **Qualify newer Konnect on copies.** Check exact requested board identity, unsaved live state, refusal when IPC fails with a locked file, undo, save/reopen, and a schematic move/rotation preserving the intended netlist. The existing schematic client's argument/response assumptions also need checking. Promote only the operations actually proven.
3. **Compare Freerouting 2.4.1 and 2.5.0 on identical copied inputs and explicit settings.** Preserve the current DSN translation/margins initially. Keep the board layer count, footprints, locks, net assignments and rules fixed. New native binaries are an optional deployment change, separate from the engine comparison. Neither an MCP endpoint nor the new IPC extension is required for this first comparison.
4. **Trial KRT only if the upgrade leaves worthwhile routing work.** Scope named nets and preserve all unrelated placement/copper. First demonstrate its treatment of each applicable class/area exception, rather than hoping native DRC will reject everything unsafe afterward. Restrict any automatic placement/net-swap features.
5. **Trial MCP Pro only for a concrete missing review workflow.** Begin with its bounded read-only profile and compare reports to the same native CLI output and local audits. Avoid installing a second overlapping write server into the stable configuration before proving a benefit.

These are proposed future evaluations; **none was executed** under this report's read-only scope. Cloud services were researched without accounts, uploads, paid jobs or contact with vendors.

### Acceptance evidence before replacing anything

| Requirement | Evidence a candidate must supply |
|---|---|
| Rule preservation | Matching PCB/project/DRU/schematic snapshots; unchanged authored rules; positive and negative examples for relevant clearance pairs, exceptions and domain barriers. Merely copying sidecars is insufficient. |
| Finishing behavior | Fewer native unconnected items with no new manufacturing/parity errors, no unintended footprint/net changes, and reviewed changes to existing copper. |
| Manufacturing geometry | `holes.py` and `text_check.py` results plus native DRC; all relevant warnings/severity settings reviewed, not just error counts. |
| Functional layout intent | `pincaps.py`; route lengths/pair mismatch; Kelvin/star shared copper; saved-fill attachment checks. Native electrical connectivity alone does not prove these. |
| Writer ownership | The live editor remains the sole writer for IPC; offline jobs obey the existing guard. Exact target/source is recorded; no silent file fallback beneath an open editor. |
| Release continuity | Existing `fab.py` snapshot/refill/parity/fresh-report/manifest behavior remains intact. A generic “export Gerbers” success is insufficient. |

The `pcbnew` scripts have a future maintenance cost: KiCad officially [deprecates SWIG bindings and currently plans their removal in KiCad 11](https://dev-docs.kicad.org/en/apis-and-binding/pcbnew/). This supports a staged backend migration when the required native capabilities are proven. It does **not** establish that replacing scripts with an MCP server will preserve their logic, or require abandoning working KiCad 10 automation today.
